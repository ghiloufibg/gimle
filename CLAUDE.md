## Project status

Phases 1–5 are implemented and committed: `gimle-core`, `gimle-module`, `gimle-os`, `gimle-worker`, `gimle-agent`, `gimle-controlplane`, `gimle-mimir`, `gimle-observability`, `gimle-fabric`, and `gimle-cli` all exist as working Maven modules with tests. `gimle-api` doesn't exist as its own module — a deliberate deviation, not a gap; probe/service-registry types live in `gimle-module` instead. `gimle-mimir` is the Raft-replicated state store's own process, split out of `gimle-controlplane` (which now talks to it over the network via `StoreClient` rather than embedding one) — real multi-node HA, failover, and etcd-style live membership change (`AddServer`/`RemoveServer`), not a single-node stand-in. Vitest coverage (`web-console-design.md` §12/M4) is done: Mock and Http repository tests for all six repositories plus a store-level error-surfacing test. `gimle-console/` is a Vite SPA (`bun run build` → `dist/index.html` + `dist/assets/*`), matching the same pattern already proven in the sibling `flow-trace-ui` project — but unlike that project, it *is* a Maven module here (`gimle-console/pom.xml`, no Java sources): `exec-maven-plugin` shells out to Bun (install/build/test) and a resources-copy step bundles the built SPA into the module's own jar under `console/**`. `gimle-controlplane` depends on that jar and `ControlPlaneMain` reads it straight off the classpath at startup (`BundledConsole.java`) — no separate build/copy/flag step, no `--console-dir`. `mvn verify` from the repo root builds and tests everything, Java and console alike, in one command (requires JDK 25 on `PATH`/`JAVA_HOME`, and `bun` on `PATH` too now).

One thing remains explicitly out of scope for the console, not an oversight: authentication (deliberate — revisit before it's ever pointed at anything beyond a single local process; see the design doc's own decision note). The other item once deferred here — an automated Playwright E2E suite — has since landed: `gimle-console/e2e/greeter-smoke.spec.ts` drives a real Chromium browser against a real running control plane, asserting the Deployments and Logs screens reflect genuine deployed-module state (opt-in, `bun run test:e2e`, not part of the module's default `bun test`/Vitest run — see `vitest.config.ts`'s own exclusion of `e2e/**`). Bringing up that "real running control plane" for the suite to test against is `gimle-smoke-tests`' job — see below.

`gimle-examples/greeter-provider` and `gimle-examples/greeter-consumer` are a real, deployable module pair (unlike the deliberately inert `hello-module`) exercising the platform's actual hosted-module capabilities end to end: real `ModuleLifecycleHooks`/`LivenessProbe`/`ReadinessProbe` implementations bundled inside each module's own jar (not left on a test's classpath, the shortcut every dynamically-loaded test fixture elsewhere in this repo uses), real APPLICATION-category logging, and a real cross-worker fabric service call (`greeter-consumer` looks up and calls `greeter-provider`'s `Greeter` service over the wire — both are `TIER_2`, dedicated workers, guaranteeing the lookup can't take the same-worker shortcut). Building this pair surfaced and fixed several real platform gaps that nothing had previously exercised end to end, all now covered by regression tests: `ModuleLayerFactory` didn't grant a hosted module's own layer readability to the platform's own (unnamed-module) classes, so a bundled hook/probe class couldn't resolve `ModuleLifecycleHooks`/`LivenessProbe`/`ReadinessProbe` at all (see `RealBundledHookAndProbeInvocationTest` in `gimle-worker`); `FabricServiceRegistry`'s client-side proxy generation and `FabricServer`'s server-side inbound dispatch both assumed a single worker-wide classloader could resolve any hosted module's own service interface, which fails for a module-private interface (the `ServiceRegistry.lookupByInterfaceName` addition and `FabricServer`'s reflect-through-the-registered-instance's-own-interface fix); and hook execution (`onInstall`/`onStart`/`onStop`/`onUninstall`) was never MDC-tagged, so even a hook's own synchronous logging miscategorized as PLATFORM output instead of that instance's own APPLICATION log (`WorkerMain#runCommand`). None of this required `gimle-api` to exist — each fix works within today's boot-only `PlatformLayer` via `requires static` + explicit `Module.addReads`, a deliberate, documented stopgap (see `ModuleLayerFactory`'s own javadoc) rather than a parallel path to migrate away from later.

`gimle-smoke-tests` (opt-in via `-Psmoke`, not part of default `mvn verify`) is the automated version of "deploy to a real server": a shared abstract fixture, `GreeterSmokeClusterSupport`, spawns a genuine `ControlPlaneMain` + `AgentMain` (+ its own `WorkerMain` child) subprocess cluster on ports distinct from `LOCAL_DEV.md`'s manual walkthrough, plus two `FafnirMain` replicas sharing one secret key file; every concrete `*IT` class in the module (`GreeterClusterTopologyIT`, `RaftResilienceIT`, `ObservabilityIT`, `SelfHealingIT`, `QuotaIT`, `AutoscaleIT`, `RollingUpdateIT` — split by topic from an original single monolithic class for clarity, a pure refactor with no behavior change) extends it and adds only the `@Test` methods for its own scenario. `GreeterClusterTopologyIT` deploys both greeter modules through the real HTTP API — the provider tenant-scoped, with a secret written through the real `/secrets/*` API before deployment — asserts both reach `ACTIVE`, that the consumer's real fabric call actually shows up in its own log, and that the provider's own log shows the secret value it fetched back via `ctx.config(...)`, then runs the console's Playwright suite against that same live cluster — one command (`mvn -pl gimle-smoke-tests verify -Psmoke`) exercises the whole stack, real processes and a real browser, start to finish.

`gimle-fafnir` (`FafnirMain`) is implemented: Gimlé's secret storage/crypto/policy, extracted out of `gimle-controlplane` into its own dedicated process kind, the same extraction shape already proven for `gimle-mimir`. `SecretCipher`/`KeyFileManager`/`KeyRing` (AES-256-GCM via the JDK's own `Cipher`, `version||keyId||iv||ciphertext-with-tag` wire format, no external crypto dependency) moved here from `gimle-controlplane.secret`; `gimle-controlplane`'s `ApiServer` no longer performs any cryptography itself, proxying `/secrets/*` and `/config/*` decryption to Fafnir over mTLS via a new `FafnirClient`. Secrets are versioned (`gimle secret set/get[--version N]/versions/delete[--destroy]`), stored as a synthetic `key@N`/`key@meta` naming convention layered over the same `/config/*` `ConfigEntry` store — no separate store schema. Authorization is real defense-in-depth (§9 of the now-implemented design doc): `ApiServer` checks and forwards the calling principal's identity as an internal claim over the mTLS-authenticated proxy hop, but Fafnir always re-runs its own independent `Authorizer.authorize(...)` (relocated to `gimle-mimir.authz` so both processes can reach it without a dependency cycle) against RBAC data it reads itself — never trusting "arrived already-forwarded" as proof by itself. Node agents (`gimle-agent`) fetch secret values straight from Fafnir over their own mTLS node identity rather than through the control plane, authorized by a node-tenant-scoping check (a `gimle:nodes` principal may read, never write/delete, a tenant's secrets only if that node currently has an active instance assignment for that tenant) — configured via `-Dgimle.agent.fafnirEndpoint`, optional (an agent with no tenant ever using secrets never needs Fafnir configured). The console's Secrets screen and CLI's `secret` subcommand are both implemented against Fafnir's own `/secrets/*` surface, not `/config/*`.

`gimle-muninn` (`MuninnMain`) is implemented: a sixth Gimlé process kind, a unified sink for logs, metrics, and traces shipped from every other process, replacing the originally-considered (and explicitly rejected) Prometheus/OTLP approach with a first-party `MuninnShipper` mechanism driven directly off the SDKs already in use (Micrometer core, the OpenTelemetry SDK) rather than adding third-party observability libraries. Storage reuses `LogFileReader`'s existing JSON-lines-per-day-file format/cursor mechanism for all three data kinds via a shared `MuninnDayFileStore` — not three separate storage engines. Shipping is two-tier: `gimle-agent` ships its own platform log plus every supervised worker's logs, metrics, and traces (workers have no outbound network identity of their own — `WorkerMain` builds a periodic `MeterSnapshotCodec` NDJSON snapshot and relays every exported span batch via `RelayingSpanExporter`/`SpanLineCodec` over the same agent↔worker control channel `ControlMessage.MetricsReport` already uses, as `MetricsSnapshot`/`TracesSnapshot`; the agent forwards each payload byte-for-byte to `MuninnShipper#shipPreparedBatch` under a new `WORKER` processKind, `{nodeId}:{workerId}`, no `gimle-mimir` changes needed), while `gimle-controlplane`, `gimle-fafnir`, `gimle-mimir`, and `gimle-andvari` each ship their own metrics/traces directly (an optional `-D{process}.muninnEndpoint` system property; `null` means "ship nowhere"), since none of the four has a supervising agent. Ingest is best-effort NDJSON over an in-memory (not persisted) shipping cursor — a process restart re-ships from "nothing shipped yet," a documented, accepted small-duplicate-window tradeoff rather than a persisted-cursor file. Auth mirrors Fafnir's own defense-in-depth pattern: Muninn holds a read-only `StoreClient` and re-runs its own independent `Authorizer.authorize(...)` check on every read, gated on the existing `ResourceKind.LOGS` (metrics and traces are treated as the same shape of thing, not given their own resource kinds); ingest itself trusts the transport the same way the agent already trusts the control plane (plaintext accepts any request; mTLS additionally verifies the peer cert's CN against the path's own nodeId/processId segment). On the read side, `gimle-controlplane`'s existing `/logs/*` proxy gains a Muninn fallback for a gone node or instance — no CLI/console change needed there — plus new `GET /metrics-history/*` and `GET /traces-history/*` APIs proxied through `ApiServer` the same way `/secrets/*` already is. `gimle-smoke-tests`' `ObservabilityIT` spawns a real Muninn replica alongside the rest of the cluster and asserts both that a log line survives its owning agent's death via the Muninn fallback and that a control plane's own request metrics round-trip through Muninn.

`gimle-andvari` (`AndvariMain`) is implemented as far as the registry process itself: a seventh Gimlé process kind, the module artifact registry — a lightweight first-party Maven-central/Nexus equivalent closing the gap where a deployment's `artifactPath` had to pre-exist on every node's own filesystem. The store (`ArtifactStore`) is immutable and content-addressed: one whole jar per `{moduleId}/{version}` coordinate beside a small `meta.json`, uploads streamed through a `DigestInputStream` to a temp file and committed with an atomic rename (never a whole-jar `byte[]` in memory, never a torn file visible after a crash), an identical re-push an idempotent no-op, a differing re-push refused with 409 — immutability is what makes downstream presence-only cache trust sound. The HTTP surface (`AndvariServer`) is `GET /artifacts` (catalog), `GET /artifacts/{m}` (versions), and `HEAD`/`GET`/`PUT`/`DELETE /artifacts/{m}/{v}`, with the jar's SHA-256 in an `X-Gimle-Artifact-Sha256` header on `HEAD`/`GET`. Auth mirrors Fafnir/Muninn's defense-in-depth pattern exactly: plaintext open (with an artifact-specific loud warning — an unauthenticated push places executable jars where agents will run them), forwarded principal wins over peer cert but is independently re-checked via `Authorizer.authorize(...)` against a new `ResourceKind.ARTIFACT`, a `gimle:nodes` identity is pull-only, and every push/delete decision is dual-audited (SLF4J line + durable `AppendAuditEvent`). `PkiBootstrapMain` mints an `andvari` leaf alongside the existing ones. Deliberately a dumb store — no `gimle-module.yaml` parsing (that validation stays in the worker's own `ModuleArtifactReader`). The consumption path is now wired end to end: `artifactPath` is optional in every workload manifest kind (blank-means-registry-coordinate via `ArtifactReference` in `gimle-core`, so no record/codec/API shape changed), admission HEAD-checks a coordinate against Andvari (404 rejects, unreachable admits sha-unset — level-triggered), the control plane and each node agent resolve coordinates through their own `ArtifactPullCache` (`gimle-module`; streamed digest-verified download, atomic commit, presence-only cache trust), `ApiServer` proxies a streaming `/artifacts/*` surface (`AndvariClient` — never a whole jar in memory, unlike the secrets proxy's buffered byte relay), the CLI gained `gimle artifact push|list|get|delete` (push derives its coordinate from the jar's own bundled `gimle-module.yaml`), a `gimle:nodes` identity may only pull coordinates its node currently holds an assignment for, and the two halves of the old stuck-at-INSTALLED failure are closed (a worker install Nack now marks the instance `FAILED`, and an agent-side resolution failure posts a durable `TRANSITION_FAILED` instance event). `AndvariRegistryIT` in `gimle-smoke-tests` proves the whole flow against a real cluster: push through the real proxy, coordinate-only deployment, real agent cache fill, `ACTIVE`. The interop-and-polish milestone is done too: a Maven-2-shaped `/repository/**` view over the identical store (GAV-path translation via `MavenCoordinates`, server-computed `.jar.sha256`, opaque `.pom`/checksum sidecars, generated `maven-metadata.xml`) lets a stock `mvn deploy`/`mvn install` target Andvari directly; `gimle-maven-plugin` gained `gimle:andvari` (spawn `AndvariMain`, port 9094) and `gimle:publish` (spawn `GimleCli artifact push` from an arbitrary module project, not self-filtered to one reactor module), with `gimle:agent`/`gimle:bootstrap` threading the endpoint through; the console's Artifacts screen lists the catalog and per-module versions (checksum, size, provenance) through the same `/artifacts/*` proxy; and `gimle-holmgang` can boot a topology with `andvari: {enabled: true}` and exercises the whole coordinate-only deploy path end to end in `registry-deploy.feature`. Andvari also has its own dedicated operator console now, `gimle-andvari-console`, the same standalone-SPA pattern `gimle-fafnir-console` already established rather than relying solely on the main console's own Artifacts screen: `AndvariServer` gained the identical `/auth/login`/`/auth/logout`/`/auth/session` cookie-session story and `/console` static-serving surface `FafnirServer` carries (same session-cookie fallback added to `resolvePrincipal`, same plaintext-mode anonymous-session carve-out, own `gimle_andvari_session` cookie and signing key under the artifact data root), and `AndvariMain` resolves and serves the bundled SPA the same `BundledSpa` way `FafnirMain` does. The console itself is a plain Vite/React/TanStack-Router SPA (never TanStack Start/SSR — the same pitfall `gimle-fafnir-console`'s own `vite.config.ts` documents avoiding), built and tested by Bun and wrapped as a no-Java-sources Maven module (`gimle-andvari-console/pom.xml`, mirroring `gimle-fafnir-console`'s exactly, bundled at `andvari-console/**`), sharing that console's exact design system (Work Sans/JetBrains Mono, the same OKLCH light/dark tokens, shadcn/ui `new-york` over Radix, the `hud-label`/`hud-panel` utilities) and its Zustand-store-over-repository-interface architecture -- `repositories/index.ts` is the single composition root, always wiring the real `Http*Repository` implementations (never a runtime Mock/Http toggle, the same posture `gimle-console`/`gimle-fafnir-console` already take), with `Mock*Repository` kept only for Vitest coverage and as a reference implementation of the same interfaces. Its emblem is an inline SVG vault-door mark rather than a bundled raster asset -- crisp at every size with nothing to keep in sync across a design iteration.

The Service abstraction, `gimle-bifrost`, `gimle-skald`, and the gateway's vhost/`SERVICE`-route extension are implemented: `ServiceSpec` (`gimle-mimir/src/main/java/com/gimle/mimir/manifest/ServiceSpec.java`) is the ClusterIP analogue named in the platform's own network-model design — a Service names itself, the `deploymentNames` set it fronts (matched by name, not a label-expression selector), and a `port`/`targetPort` pair. `NetworkPolicySpec` lives alongside it as the NetworkPolicy analogue (`allowedCallerTenantIds`, deny-by-default once a policy exists for a tenant), durably persisted through `gimle-mimir`/`StoreClient` the same way `ServiceSpec` is (`StateMutation.PutNetworkPolicy`/`RemoveNetworkPolicy`, `gimle-controlplane`'s `NetworkPolicyRegistry` a thin `StoreReader`/`MutationSink` facade — a policy created against one control-plane replica is visible to every other replica and survives a restart). Enforcement is real and now covers both scopes: `gimle-agent`'s `NetworkPolicyRelay` polls `GET /networkpolicies` and relays the full current set — tenant-wide and per-deployment-scoped alike — to every supervised worker over the existing control channel (`ControlMessage.NetworkPoliciesUpdated`, carrying the wire-transferable `NetworkPolicyRule`, not `NetworkPolicySpec` itself — `gimle-core` can't depend on `gimle-mimir`; `NetworkPolicyRule` gained its own `deploymentNames`/`appliesToDeployment` mirroring the manifest type's). `FabricServer.checkNetworkPolicyPermitted` (`gimle-fabric`) independently re-checks the caller's wire-carried tenant identity against the relayed policy set before dispatch, resolving each call's own target deployment name via a new `deploymentNameOf` lookup (backed by the worker's `InstanceIdentityRegistry` in production) so a deployment-scoped rule is checked against the one deployment it actually names — a target with no known deployment identity is never matched by a scoped rule, only ever by a tenant-wide one. `gimle-controlplane`'s `ServiceReconciler` is level-triggered like every other reconciler here, recomputing each Service's live backing-instance endpoint set from the current store snapshot every tick; `ApiServer` exposes `POST`/`GET`/`DELETE /services`, `GET /services/{name}/endpoints` (`{"name","port","targetPort","endpoints":[{"host","port"}]}`), and the equivalent `/networkpolicies*` CRUD, RBAC-gated via `ResourceKind.SERVICE`/`ResourceKind.NETWORK_POLICY`. A hosted (non-Vessel) module can now participate in that endpoint resolution too: `ModuleContext.reportPort(name, port)` (`gimle-module`) folds into the same per-tick `MetricsReport` a Vessel's own port allocation already rides (`gimle-core`), landing in `InstanceObservation.ports()` (`gimle-agent`) the identical way — closing the gap where `ServiceEndpointResolver.solePort()` could only ever resolve a Vessel instance. Real, shipped listener-side tenant enforcement also landed independent of `NetworkPolicySpec`: `FabricServer.dispatch` (`gimle-fabric`) independently re-checks a target's `ServiceExport.allowedTenantIds` against the caller's wire-carried tenant identity, closing the bypass where a caller could dial the raw catalog address directly and skip the caller-side filter. `gimle-agent` gained a per-node service proxy, package `com.gimle.agent.bifrost` ("gimle-bifrost"), off by default (`-Dgimle.agent.bifrostEnabled=true`): `BifrostProxy` is level-triggered the same way, polling a `ServiceSource` on a fixed interval and keeping one loopback-bound `ServiceListener` per currently-known Service, round-robin-forwarding to live endpoints — embedded in the agent, not a new process kind. `BifrostProxy` also polls the same `NetworkPolicySource` `NetworkPolicyRelay` does and fails a Service's listener closed (refuses every new connection, endpoints untouched) whenever a `NetworkPolicySpec` currently applies to that Service's tenant/deployment — the deliberate, permanent limit of what Bifrost can enforce: unlike `FabricServer`, which decodes the fabric wire protocol and reads the caller's wire-carried tenant claim, Bifrost relays opaque bytes for whatever protocol the caller speaks, so it has no caller identity to check a policy's `allowedCallerTenantIds` against and fails closed rather than silently bypass the policy. `gimle-skald` (`SkaldMain`) is a genuinely new, eighth Gimlé process kind, the first added since Andvari: a hand-rolled UDP DNS responder answering `A` queries for `<service>.<tenant>.svc.gimle.local`, resolved the same way `gimle-bifrost` resolves them — polling the control plane's `/services/*` API, never `gimle-mimir` directly — and deliberately plaintext-only for this first slice, since a DNS-over-UDP responder has no TLS story to opt into the way an HTTP-based process does. `gimle-gateway` gained hostname-constrained (vhost) routing alongside its existing exact-path routing (fully backward-compatible — a route with no `HOST` segment still matches any host) and a new `SERVICE <path> <serviceName>` route kind (`GatewayRoute.ServiceRoute`/`ServiceEndpointCache`) that resolves and round-robins over a declared Service's live endpoints the same TTL-cache posture the existing `VESSEL` route already established. `gimle-gateway` also gained TLS termination (`GatewayHooks#createHttpServer`, mirroring `ApiServer`'s own `TransportProtocol`/`SslContexts.forMutualTls` posture — plaintext by default, `-Dgimle.transport.protocol=tls` opts in, `wantClientAuth` rather than `needClientAuth`). Separately, `hilmir doctor` (`gimle-hilmir`) gained an advisory-only (`INFO`-severity) hazard, `MAKES_OUTBOUND_CALLS`, flagging a module's own outbound `Socket`/`SocketChannel`/`HttpClient` construction — informational visibility into egress surface, not enforcement, consistent with egress control staying deferred to Tier-3 network namespaces (`SecurityManager` is permanently removed as of Java 25, so no in-process egress mediation is possible today).

`gimle-saga` (`SagaMain`) is implemented: a standalone test-run report server, deliberately *not* one of the deployed cluster's own process kinds (unlike `gimle-mimir`/`gimle-fafnir`/`gimle-muninn`/`gimle-andvari`/`gimle-skald`) — a local development tool, unauthenticated, TLS-free, and loopback-bound by default, started next to a build via `-Dgimle.saga.*` system properties rather than the flag-parsing style the cluster process kinds use. It ingests `SagaEvent` NDJSON streams from test runs anywhere in the reactor, stores each run durably under a flat-file `SagaStore` (`runs/{runId}/events.ndjson` the append-only authoritative record, `meta.json` a derived summary, plus a reconstructable cross-run flake ledger), derives a flaky-test scoreboard (`flakeRate` = occurrences over runs-seen, `score` = `flakeRate * runsSeen`, `quarantined` keyed off a test's own `@Tag("flaky")`), and serves the whole record — runs, live NDJSON event tails, the flake scoreboard, per-test history — over a small JSON HTTP API (`SagaServer`) plus a bundled web console at `/console` (`gimle-saga-console`). It is fed two ways, both best-effort and dormant unless explicitly configured (a Saga server being down or absent never fails a test run): `gimle-core`'s own `SagaTestListener` (a JUnit `TestExecutionListener`, active reactor-wide once `-Dgimle.saga.endpoint` is set) streams any module's ordinary per-test results here live as they run, and `gimle-holmgang`'s `SagaShipper` additionally ships its own Gherkin/Fenrir/Surtr/topology results here as attachment events (`POST /api/import`, folding into an already-open run via `?runId=`) — distinct from, and not a replacement for, Holmgang's own internal `com.gimle.holmgang.saga` package, which writes Holmgang's own per-run `holmgang-report.json`/`holmgang-report.html` regardless of whether this server is running at all. Neither the control plane nor the CLI talks to it — it has nothing to do with Skald/Bifrost/DNS-style service discovery or any deployed-cluster API; `gimle-maven-plugin` gained `gimle:saga` (ensure a server is running, reusing a healthy one already listening rather than spawning a duplicate), `gimle:saga-stop`, and `gimle:saga-import`/`gimle:saga-verify` as the only tooling that drives it.

## What Gimlé is

A fully-Java application platform that combines Karaf/OSGi-style dynamic module lifecycle with Kubernetes-style declarative orchestration (self-healing, scaling, load balancing, service discovery, observability) — implemented entirely on the JVM with no containers, no external orchestrator, and no non-Java runtime dependencies.

Non-goals worth remembering when reviewing design choices: not OSGi-compliant (no Felix/Equinox, JPMS `ModuleLayer` instead), not Kubernetes-API-compatible (no CRDs/kubectl/OCI images), not a general untrusted-workload runtime, and not built on Spring Boot/Quarkus/Netty/an existing service mesh — the module system, supervisor, control plane, and service fabric are the point of the project, not glue over existing frameworks.

## Host language & load-bearing JDK features

Java 25 (LTS). These are architectural dependencies, not incidental choices — don't suggest alternatives that bypass them:

- `ModuleLayer` / dynamic JPMS — module system foundation, replaces OSGi classloading
- `Process` API (`onExit`, `destroyForcibly`, `pid`) — worker JVM supervision
- FFM API (`Linker`, `MemorySegment`) — direct libc/syscall access (namespaces, CPU affinity), for the deferred kernel-level resource limiter and Tier 3 namespaces (not built yet, see "Core architecture" below); **no JNI, no native code anywhere**, now or once it lands
- Virtual threads (unpinned, JEP 491), Scoped values (JEP 506), Structured concurrency
- JFR event streaming — per-module resource accounting
- AOT cache (JEP 483/514/515) — sub-second worker JVM startup
- `jlink` / `jpackage` — minimal per-node-role runtime images
- Sealed interfaces + records for state/event/protocol types

## Core architecture: tiered isolation

The central design claim is container-grade isolation and classloader-grade density in one system, selected per workload via the module manifest:

```
Machine (Node Agent, JVM)
 └── Worker JVM  ── memory/CPU boundary, own -Xmx, own resource limiter
      └── Module ── ModuleLayer + classloader, soft accounting
           └── Instance ── bounded virtual-thread scheduler
```

- **Tier 1** — module in a shared worker JVM. Millisecond deploys, classloader-level isolation, soft JFR-based accounting. Density win.
- **Tier 2** — module in a dedicated worker JVM. Sub-second deploy (AOT cache), hard `-Xmx`/CPU ceiling, independent crash domain. Kubernetes-equivalent guarantee, available per module.
- **Tier 3** — worker JVM in a Linux namespace (via FFM `unshare`/`setns`). For hostile-neighbour scenarios.

**Platform independence first, platform-specific enforcement later** (deliberate design revision — see `claudedocs/phase2-worker-runtime-design.md` §1 and §2.4). Tier 1/2 limits are enforced today entirely through the portable `ResourceLimiter` interface (`gimle-os`) and its only current implementation, `PortableJvmFlagsResourceLimiter` — `-Xmx`/`ActiveProcessorCount`, identical on Linux/macOS/Windows, zero OS-specific code. Real kernel-level enforcement (cgroup v2 on Linux via plain `java.nio.file` I/O against `/sys/fs/cgroup` — no containerd/runc equivalent needed) is a deliberately deferred second `ResourceLimiter` implementation, not a parallel path built alongside the portable one. Tier 3 (FFM downcalls to `unshare`/`setns`) is unimplemented on every platform today and rejected outright (`GimleIsolationException`) rather than silently downgraded — "not built yet," not "your platform doesn't support it." Don't add cgroup/FFM code, or platform-detection branching, to satisfy a capability nothing yet consumes — that's exactly the speculative work this revision avoids.

## Node topology

Eight Java process roles, nothing else runs on the machine:

- **Node Agent** — one per machine, owns worker `Process` lifecycle and resource-limit assignment (portable JVM flags today, see "Core architecture" above), reports capacity/state, never runs user code.
- **Worker JVM** — hosts module instances in `ModuleLayer`s, reports health/metrics to its agent, disposable by design.
- **Control Plane** (`gimle-controlplane`) — API server, scheduler, reconcilers; one or more stateless JVMs, talking to the store cluster over the network rather than embedding one.
- **Store** (`gimle-mimir`) — the Raft-replicated state store, its own process kind with its own Raft-peer and client ports; multi-node HA, failover, and etcd-style live membership change are implemented and tested, not deferred.
- **Fafnir** (`gimle-fafnir`) — the secrets vault, its own process kind holding the master key ring and every secret encrypt/decrypt operation; `gimle-controlplane` proxies to it over mTLS rather than embedding crypto, and node agents fetch secret values from it directly (see "Project status" above).
- **Muninn** (`gimle-muninn`) — the observability sink, its own process kind holding day-bucketed logs, metrics, and traces shipped from every other process; `gimle-controlplane` proxies `/logs/*` (as a fallback for a gone node/instance), `/metrics-history/*`, and `/traces-history/*` reads to it, and `gimle-agent`/`gimle-controlplane`/`gimle-fafnir`/`gimle-mimir` each ship to it directly over an optional `MuninnShipper` (see "Project status" above).
- **Andvari** (`gimle-andvari`) — the module artifact registry, its own process kind holding an immutable, content-addressed store of module jars behind a push/pull/list `/artifacts/*` API (see "Project status" above for what is and isn't wired to it yet).
- **Skald** (`gimle-skald`) — cluster DNS, its own process kind: a hand-rolled UDP responder (`SkaldMain`) answering `A` queries for `<service>.<tenant>.svc.gimle.local`, polling the control plane's `/services/*` API the same way `gimle-bifrost` does rather than reading `gimle-mimir` directly (see "Project status" above).

Node/worker/module failure are distinct events with distinct recovery costs (seconds/sub-second/milliseconds) and are reconciled accordingly.

## Module system

- A module artifact = JAR + `gimle-module.yaml` (name, version, required-module version ranges, exported services, isolation tier, resource requests/limits, health probe class, lifecycle hooks).
- Each instance gets its own `ModuleLayer`/classloader parented on a shared platform layer (JDK + Gimlé service API). Hoisting common libraries into shared layers is the density lever and must be an explicit, measured decision.
- Lifecycle: `INSTALLED → RESOLVED → STARTING → ACTIVE → STOPPING → UNINSTALLED` (deliberately OSGi-like).
- Hot redeploy: install new version alongside old, drain, dispose old layer.
- **Classloader leak detection is first-class**: after undeploy, a `PhantomReference` to the disposed layer's loader is held; if it survives a configurable window, a leak is reported with the retaining path via heap walk. Redeploy-in-a-loop with flat metaspace is a mandatory acceptance test. A module that leaks anyway can be moved to Tier 2, where undeploy just kills a JVM.

## Control plane

- **API server** accepts manifests (desired state), persisted through a `StoreClient` to the `gimle-mimir` state store cluster over the network (no embedded/in-process store anymore).
- **State store** (`gimle-mimir`) — its own Raft-replicated process kind, decoupled 1:N from `gimle-controlplane`'s own replica count; multi-node HA and etcd-style live membership change (`AddServer`/`RemoveServer`, one server at a time) are both implemented and covered by real multi-node tests, not a Phase-5-deferred single-node stand-in.
- **Scheduler** places instances by resource requests, isolation tier, anti-affinity, and machine load — a two-dimensional bin-packing problem (resources × tier). Cross-node anti-affinity is opt-in per deployment (`placement: {antiAffinity: true}` in the manifest), not an unconditional guarantee — a manifest that omits it can and does land every replica on the same node even when other healthy nodes are available; see "Horizontal scaling" below for why it stays opt-in rather than always-on.
- **Reconcilers** — one control loop per resource kind, **level-triggered, not edge-triggered**: must converge from any starting state, including after missing every event. This is the hardest-to-test and most important correctness property in the codebase — reconciler changes need convergence tests from arbitrary starting states, not just the happy-path transition.
- **Membership/failure detection** — SWIM-style gossip over UDP between node agents, off the control plane's critical path.

## Service fabric

- Modules publish/consume services via a registry keyed by interface + version.
- Same-worker calls are direct in-JVM invocations (no serialization/network/proxy). Cross-worker-same-machine uses a Unix domain socket with a compact binary codec. Cross-machine uses the same codec over TCP with virtual-thread-per-connection.
- Load balancing prefers locality: same-worker → same-machine → remote (least-outstanding-requests), with circuit breaking/outlier ejection at the registry level. Same-machine isn't a hard cutoff: once every same-machine candidate is busier than the least-loaded remote one, the remote tier is admitted into selection too, so a single saturated same-machine replica spills over instead of absorbing all traffic while remote replicas sit idle.

## Health, scaling, self-healing

- Probes are Java interfaces (`LivenessProbe`/`ReadinessProbe`) called directly by the worker — no HTTP, no sidecar.
- Tiered self-healing matches isolation tiers (module dispose+reinstantiate → worker `destroyForcibly`+respawn → machine-level reschedule), with automatic escalation and `CrashLoopBackOff`-style backoff.
- Horizontal scaling driven by per-module metrics (request rate, latency, queue depth, allocation rate); scale-up may pack onto the same worker, which is why anti-affinity must stay configurable.

## Observability

Micrometer for per-module metrics, OpenTelemetry tracing propagated via `Context.wrap` capture-and-restore across virtual-thread boundaries (including across in-JVM hops — not `ScopedValue`: OTel's own `Span.current()`/`Baggage.current()` read OTel's own `Context`, so a `ScopedValue` carrying trace state would still need `Context.makeCurrent()` re-entered inside it to be useful, i.e. both mechanisms would end up coexisting, not one replacing the other), JFR-backed per-module allocation/CPU accounting (what makes Tier 1 soft limits enforceable), and a structured, queryable event log of every lifecycle/reconciliation decision.

- `gimle-fabric` — service registry, three-path invocation, load balancing, circuit breaking, gossip membership
- `gimle-observability` — metrics, tracing, JFR accounting, event log
- `gimle-cli` — control-plane client, agent launcher, worker launcher
- `gimle-console` — the web console SPA (no Java sources; Bun/Vite build wrapped as a thin Maven module so `mvn verify` covers it), bundled into `gimle-controlplane`'s classpath; its own `e2e/` holds the opt-in Playwright suite

- `gimle-holmgang` — test-only functional cluster validation, opt-in via `-Pvalidation` (never default `mvn verify` or CI): boots real subprocess clusters from declarative YAML/DSL topologies (dynamic ports; plaintext or full mTLS incl. agent CSR bootstrap; optional Loki fault proxies for partitions), validates them through Gherkin scenarios over the Heimdall event-driven condition harness (no sleeps/polling in test code, forensic failure reports), and can subject a running cluster to a randomized converge-then-strike chaos soak via Fenrir (`com.gimle.ragnarok.fenrir`: a seeded fault scheduler over a worker-kill/store-bounce/leader-bounce/control-plane-bounce/link-cut palette, one fault in flight at a time behind quorum and control-plane-floor guards, every strike gated on full recovery through Heimdall and recorded in a replayable `ChaosLedger` — the `chaos-soak.feature` scenario), and can drive declarative scale/churn/performance burns via Surtr (`com.gimle.ragnarok.surtr`: the kube-burner equivalent — a YAML workload runner that floods the real control-plane API with templated deployments/tenants at a controlled QPS via a token bucket, reusing one built reference module under N names, measuring per-phase instance startup latency from the platform's own lifecycle event log (not harness polling), API latency, failures, and placement spread, gating on `maxFailedSubmissions`/`maxNeverActive` plus opt-in latency tripwires, and writing a timestamped diffable `summary.json`+NDJSON report; `SurtrIT` runs only under `-Dgimle.surtr.workload=<name|path>` with `-Dgimle.surtr.scale=N`, skipping via a JUnit assumption otherwise), and after every `-Pvalidation` run emits a single unified run report via Saga (`com.gimle.holmgang.saga`: a process-wide `SagaCollector` fed by a `SagaCucumberPlugin` (Gherkin scenario/step results) and a `SagaJUnitListener` (the plain-JUnit `*IT` classes folded into the same shape, so the record is complete whatever a test's type — the Cucumber engine counted once by the plugin, `SurtrIT` kept to its own richer section), plus folded-in Fenrir ledgers, Surtr measurements, and booted topologies, flushed once at JVM shutdown to a versioned `holmgang-report.json` under `target/holmgang/saga/<run-id>/` plus a self-contained `holmgang-report.html` beside it — the bundled Saga console template (`src/test/resources/saga/saga-console.html`) with that run's data embedded, opening directly in a browser the way surefire's HTML reports do, with Gherkin/JUnit sections and run-to-run baseline diffing); see its README for the runbook. Both engines are consumed from `gimle-ragnarok` rather than defined here -- what remains under this module's own `surtr` package is the harness-side `ExampleModuleJarSource` adapter, and its `fenrir` package is gone entirely
- `gimle-ragnarok` — the chaos (Fenrir) and stress/load (Surtr) engines as a shipping library plus their own CLI (`RagnarokMain`: `ragnarok preflight|chaos|stress|replay|report`, hand-rolled verb dispatch like `gimle-hilmir`, no picocli). Extracted out of `gimle-holmgang` so the same engines can be pointed at a real, already-running cluster instead of only an in-JVM harness-booted one: the `ClusterTarget` seam is the decoupling point, with `EndpointClusterTarget` reading a `--target` YAML document and driving a live cluster over its real endpoints. Faults needing process control or network interposition (Loki proxies, worker kills) stay available only to a harness-backed target -- an adapter without process control reports that honestly rather than failing. `chaos`/`replay` carry the tool's one safety catch: a plan naming any destructive (non-pure-network) fault kind requires `--confirm-destructive`. Not a deployed cluster process kind and not test-only either; documented for operators at `gimle-docs/docs/reference/ragnarok-reference.md`
- `gimle-saga` — standalone test-run report server, its own process (`SagaMain`), not one of the deployed cluster's own process kinds: ingests `SagaEvent` NDJSON from test runs anywhere in the reactor, stores each run in a flat-file `SagaStore`, derives a cross-run flaky-test scoreboard, and serves runs/live tails/scoreboard/per-test history over a small JSON HTTP API plus a bundled console; fed by `gimle-core`'s `SagaTestListener` and `gimle-holmgang`'s `SagaShipper`, both best-effort and dormant unless `-Dgimle.saga.endpoint` is set
- `gimle-saga-console` — Saga's own web console SPA (no Java sources; Bun/Vite build wrapped as a thin Maven module so `mvn verify` covers it), bundled into `gimle-saga`'s classpath and served at its own `/console`, the same standalone pattern `gimle-fafnir-console`/`gimle-andvari-console` established
- `gimle-examples/hello-module` — a minimal, deliberately inert real module artifact (its manifest declares distinct `resources.request`/`resources.limit` values), used as a live deployable fixture for manual verification and QA passes, not exercised by any module's own automated test suite

## Conventions (binding, not optional)

- **Build**: Maven.
- **Formatting**: Google Java Format, enforced via `fmt-maven-plugin` in CI and pre-commit.
- **Method naming**: standard Java `camelCase` everywhere — production code, JUnit lifecycle hooks (`@BeforeEach`/`@AfterEach`/`@BeforeAll`/`@AfterAll`), and private/helper methods in test classes. The one exception: methods directly annotated `@Test` are `snake_case`, so a test's name reads as a sentence describing the behavior it verifies. Enforced by two Checkstyle `MethodName` instances (one scoped to `@Test` methods, one to everything else) via XPath-based suppressions in `checkstyle-suppressions.xml`, not inline `@SuppressWarnings`.
- **No checked exceptions anywhere.** Gimlé failures use dedicated unchecked types in `gimle-core` (`GimleResolutionException`, `GimleLifecycleException`, `GimleSchedulingException`, `GimleManifestException`, `GimleClusterException`, `GimleIsolationException`, `GimleCodecException`, `GimleSecretsException`, `GimleVolumeException`), all extending `RuntimeException`. Control-plane errors map to structured API responses, not propagated stack traces.
- **Immutability**: records / `List.of`/unmodifiable collections preferred everywhere feasible. Desired state, observed state, and reconciliation events are strictly immutable snapshots — a reconciler reads a snapshot and returns actions, never mutates in place.
- **`final`** on variables, fields, and parameters wherever possible.
- **No Lombok.** Plain Java (records, standard getters/constructors).
- **`@SuppressWarnings` is a last resort, not a shortcut.** Before reaching for it, fix the actual type issue: extract the unchecked cast into a single well-named, documented helper (e.g. `Json.asObject`/`Json.asObjectList` in `gimle-core`) so at most one place in the codebase carries the suppression instead of every call site; or restructure to avoid the cast entirely. Scattering `@SuppressWarnings` through test methods to silence casts from a shared untyped/erased API (JSON trees, reflective lookups) is exactly the case a shared helper should absorb instead. The narrow case where it's genuinely unavoidable — a typesafe heterogeneous container keyed by a `Class<T>` witness token (see `SimpleServiceRegistry.lookup`) — is the reference example for "no other option"; if you can't point to something structurally equivalent, don't add the annotation.
- **No JNI, no native code.** OS interaction only via `java.nio.file` or FFM downcalls.
- **No backward-compatibility concern by default.** Gimlé has no external users or deployments today, so when designing, refactoring, or adding a feature, do not preserve old behavior, old flags, old wire/file formats, or old call signatures for compatibility's sake, and do not add deprecation shims, feature flags, or dual-path fallbacks to ease a future migration that has no present user. Change signatures, rename things, break formats, and update every call site directly. This only applies unless the user explicitly asks for backward compatibility in a given case.
- **Logging**: SLF4J API + Logback binding, configured once in `gimle-core`, inherited by all modules; hosted modules see the platform logging API through the shared layer rather than bundling their own binding.
- **Comments**: clear names/small methods over Javadoc; add a comment only where logic is genuinely non-obvious (e.g. layer parent selection, leak-detection reference handling, FFM struct layouts, reconciler convergence edge cases). Applies to test code too.
- **Test coverage**: cover both happy paths and failure paths (unresolvable dependency, version conflict, probe timeout, worker OOM, network partition, no feasible placement, corrupt manifest, cgroup write failure). Reconcilers additionally require convergence tests from arbitrary starting states; the module system requires a repeated-redeploy leak test; the supervisor requires kill-and-recover tests at every tier.
- **Git hooks**: `commit-msg` rejects any commit message mentioning an AI assistant (Claude, Copilot, ChatGPT, etc.) — do not attribute commits to AI tooling. Commit messages follow Conventional Commits (`feat`, `fix`, `chore`, `refactor`, `docs`, `test`, ...), short subject, max 3 lines total. `pre-commit` is currently disabled (a full `mvn verify` per commit stopped being practical as the reactor grew) — see `.githooks/pre-commit` for the reasoning and how to re-enable it.
- **Repo hygiene**: commit only essential source and config. No generated reports or ad-hoc markdown files except `CLAUDE.md`/`README.md`/`REQUIREMENTS_MATRIX.md`/`RTM.md`/`UAT_CHECKLIST.md`/`FORSETI.md`, and no generated JSON files except `requirements-matrix.json`/`rtm.json`/`uat-checklist.json`/`forseti.json` (see "Keep `REQUIREMENTS_MATRIX.md` and `RTM.md` in sync" and "Keep `FORSETI.md` in sync" below — the `.md` files are rendered from the `.json` files, not authored directly; `FORSETI.md` is the one whose doctrine prose is hand-written around generated blocks). A Forseti run's own findings report is never committed — it is published as a dated artifact and indexed by one row in `FORSETI.md`'s release-history table. `claudedocs/` is gitignored.
- **No `claudedocs/` references from committed files, and no design/plan references in comments or Javadoc at all.** Comments, Javadoc, and config files under version control (`pom.xml`, `.mvn/**`, `*.java`, `*.xml`, `*.yaml`) must never point a reader at a `claudedocs/*.md` path — `claudedocs/` is gitignored and local to one checkout, so a reference to it from a committed file is a dangling link for anyone else who clones the repo, or once that local doc is deleted. More broadly, no comment or Javadoc may cite `gimle-PROJECT-v2.md`, a phase number, a design-doc section, or any other planning/process artifact, checked in or not — a comment describes the code it sits next to (what it does, and where genuinely non-obvious, why it's written that way), never "per the design," "see Phase 2," or similar. Someone reading the code with no access to the project's planning history must be able to understand it fully from the code and its comments alone; anything else reads as unprofessional and meaningless to that reader. State the *why* inline instead of citing an external doc or section for it.
- **Keep `gimle-docs` in sync.** When a change affects module roles, cross-component architecture, the CLI surface, the manifest schema, or a convention covered on the documentation site, update the relevant `gimle-docs/docs/**` page(s) as part of the same change — not as a deferred follow-up. Treat a page going stale relative to the code it describes as a defect in that change, the same way an unupdated test would be. Verify with `mvn -P docs -pl gimle-docs install` (or `mvn gimle:docs` for the full pipeline including aggregated Javadoc) before considering the change done.
- **Keep `REQUIREMENTS_MATRIX.md`, `RTM.md`, and `UAT_CHECKLIST.md` in sync.** All three live at the repo root and track the platform's requirements and their traceability to real test coverage, but none of them is hand-edited: **`requirements-matrix.json` and `rtm.json` (also repo-root) are the structured source of truth**, and the three `.md` files — plus `uat-checklist.json` — are generated views rendered from them by `scripts/generate_requirements_docs.py`. Treat any of the five going stale relative to the code they describe as a defect in that change, the same way an unupdated test would be. The Holmgang RTM coverage gate (`gimle-holmgang`'s `com.gimle.holmgang.rtm` package, see its own README section) reads `rtm.json` directly, not `RTM.md` — another reason the JSON must never drift from what the rendered Markdown claims.
  - **Adding a feature/capability**: assign it the next unused sequential `GIMLE-NNN` ID (never reuse or renumber an existing ID) and add its full entry to `requirements-matrix.json`'s `requirements` array — module, category, user story, Gherkin scenario steps, source location(s), test coverage, confidence, status — as part of the same change. Then add the corresponding entry to `rtm.json`: `"status": "New"`, and `"coverage": "Covered"` only if a real Holmgang Cucumber `.feature` scenario already exercises it end to end (Holmgang's own plain-JUnit `*IT` classes and every other module's unit/integration tests do not count — see `rtm.json`'s own `metadata.coverageRule`); otherwise `"Not Covered"` with a concrete `gapNote`. Finish by running `python3 scripts/generate_requirements_docs.py` from the repo root to regenerate `REQUIREMENTS_MATRIX.md`, `RTM.md`, `uat-checklist.json`, and `UAT_CHECKLIST.md` — never hand-edit those four, a direct edit is silently discarded on the next regeneration.
  - **Removing or fundamentally changing a requirement's behavior**: never silently delete or renumber its entry. In `requirements-matrix.json`, mark its status `Removed` (with the commit/reason in `statusDetail`) or update its description, Gherkin steps, source, and test coverage to match the new behavior. In `rtm.json`, update its `status` to `Removed`/`Modified` accordingly and re-verify its `coverage` from scratch — a passing Holmgang scenario against the old behavior does not carry over to the new one. Then regenerate the four rendered files the same way.
  - All of this is reverse-engineered from the actual codebase, not aspirational — an entry must reflect what the code and its tests actually do, not what a manifest/design doc says they should do.
  - `uat-checklist.json` carries one piece of state the others don't: per-item UAT sign-off (`signedOff`/`signedOffBy`/`signedOffAt`). Regenerating merges by ID — an existing item's sign-off survives untouched, a new ID is added unsigned, and an ID no longer in `rtm.json` is dropped — so re-running the generator after a requirements change never resets sign-off on unrelated items.
- **Keep `FORSETI.md` in sync.** `FORSETI.md` (repo root) is the standing pre-release QA doctrine: the black-box agent-fleet method, its four environments (Forge/Midgard/Fleet/Vault), the persona roster, the objective-plus-oracle scenario catalog, the finding template, severity taxonomy and deduplication protocol, and a per-requirement coverage table measured directly against `requirements-matrix.json`. Its doctrine prose is hand-written; every table between `<!-- forseti:generated … -->` markers is rendered from **`forseti.json`** (scenarios, environments, personas, and the classification of each `GIMLE-NNN` as user-observable / internal / out of scope) plus `requirements-matrix.json`/`rtm.json` by `python3 scripts/generate_forseti_docs.py` — never hand-edit a generated block. `scripts/generate_requirements_docs.py` calls that generator too, so regenerating the requirements docs re-renders Forseti's tables in the same step.
  - **Adding a `GIMLE-NNN`** means placing it in `forseti.json` as well: either in the `requirements` list of one or more scenarios (it is user-observable and the fleet must reach it), or in an `internal`/`outOfScope` group with a reason. An unplaced requirement defaults to user-observable-and-unreached; the generator prints a `FORSETI GAP` and exits non-zero if the fleet's reach drops below `fleetCoverageTarget` or a requirement has no mechanism at all, so this is loud, not silent.
  - **Changing or removing a requirement's behaviour** means re-reading every scenario whose `requirements` name it — a scenario written against the old behaviour does not carry over — and updating its objective/oracle or moving the ID.
  - A Forseti run's findings report is published as a dated artifact and is never committed. The only thing a run writes back to the repo is one row in `FORSETI.md`'s hand-maintained release-history table (§10), which is outside every generated block.
