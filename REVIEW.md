## Addendum: fully-qualified-name (FQN) sweep

Several earlier findings (`StoreClient.java`, `RolesCommand.java`, `RetentionSweeper.java`, `CatalogDelta` in `AgentMain.java`) flagged the same specific pattern: a type referenced by its fully-qualified name inline in code instead of being imported, breaking the file's own otherwise-consistent import style. This addendum is a targeted, codebase-wide sweep for that one pattern specifically, across all 20 in-scope backend modules (`gimle-console`/`gimle-fafnir-console` still excluded). Unlike the sections above, this pass was done with a pattern search across every `.java` file followed by manual triage — not a fresh per-module reading agent — to filter out javadoc `{@link}` references (a normal, accepted Java idiom, not a readability defect), string literals that merely *look* like a type name (reflection method signatures, YAML/text-block descriptor content, process-argument class names for `java -cp`), and genuine positive matches. Findings below are new (marked **(new-fqn)**) unless they confirm a finding already listed above, in which case they're called out as such rather than double-counted.

The pattern turns out to be systemic rather than isolated — nearly every module has at least a few instances, split roughly evenly between production code (a handful of files) and test code (the majority, especially JDK collection/concurrency/crypto types in test fixtures). The most notable production-code cluster is `gimle-mimir`, where `com.gimle.core.authz.Role` alone is referenced unimported in five separate files.

## Scope and exclusions

This review looks at exactly one axis: **how easy this code is for a human maintainer — who did not write it — to read, understand, and safely change.** It intentionally excludes performance, optimization, security, and correctness/bug-hunting; a finding here is about clarity, not whether the code is fast, safe, or right.

Concretely, each agent looked for: unclear/inconsistent naming, oversized methods/classes mixing abstraction levels, stale or restating comments (and comments that explain real *why*), duplicated logic, tangled control flow, unexplained magic values, inconsistent conventions within a module, dead/commented-out code, overly dense/clever code, weak test names/assertions, and violations of this repo's own committed conventions (Google Java Format, `@Test` snake_case vs. camelCase elsewhere, no Lombok, immutable records, no checked exceptions, and — notably — the rule that no comment may cite `claudedocs/` or any other planning artifact).

**Excluded from this pass by explicit request:** `gimle-console` and `gimle-fafnir-console` (the two frontend SPAs).

**Included:** all 20 remaining Maven modules, including the tiny `gimle-examples/*` modules, `gimle-smoke-tests`, and `gimle-docs`.

The single most common theme across the whole codebase is **duplication a human maintainer has to keep in sync by hand** — repeated dispatch/handler skeletons, repeated manifest/YAML (de)serialization helpers, repeated test fixtures — usually well-commented in isolation but requiring the same edit in 3–8 places when it changes. The second most common theme is a handful of **outsized "do everything" classes** (`ApiServer`, `StateStore`, `AgentMain`, `WorkerMain`, `GreeterSmokeClusterSupport`) that are internally well-organized but too large to hold in working memory at once. Third, several modules have one or two **comments that cite a planning artifact** (`claudedocs/...`, `QA_FINDINGS.md`, a phase/section number) or have **gone stale relative to the code**, which this repo's own conventions explicitly flag as a readability defect. Fourth — surfaced by the dedicated addendum below — **fully-qualified names used inline instead of being imported** is a codebase-wide habit rather than an isolated slip: it shows up in nearly every module, concentrated in test fixtures (JDK collection/concurrency/crypto types) but present in production code too, most notably `com.gimle.core.authz.Role` going unimported across five separate files in `gimle-mimir`.
