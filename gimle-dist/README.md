# Gimle Dist

`gimle-dist` is a `pom`-packaged reactor module with no Java sources of its own — only
`maven-assembly-plugin` descriptors and the two `sh` wrapper scripts every archive ships. It packages
the platform's already-built jars into three audience-specific distribution tarballs. Every
dependency it declares exists purely so `maven-assembly-plugin` has a resolved dependency graph to
pick jars out of; `gimle-dist` itself never calls any of this code — each assembly descriptor selects
its own subset of that graph via `<includes>`/`<excludes>`.

## What gets built

`mvn -pl gimle-dist -am package` (or `install`) produces three `tar.gz` archives under `target/`:

| Archive | Descriptor | Contents |
|---|---|---|
| `gimle-platform-<version>.tar.gz` | `src/main/assembly/platform.xml` | Every process-kind jar (`gimle-mimir`, `gimle-controlplane`, `gimle-agent`, `gimle-worker`, `gimle-fafnir`, `gimle-muninn`, `gimle-andvari`, `gimle-pki`, `gimle-hilmir`, `gimle-cli`) plus their transitive runtime dependencies, flattened into one `lib/` directory — the single classpath every process role's own launch command (generated by Hilmir's `LaunchPlanner`) points at. `gimle-gateway`'s jar (a hosted module, not a process kind) is excluded from `lib/` and placed under `modules/` instead, where nothing puts it on a classpath. Ships both `bin/gimle` and `bin/hilmir`. |
| `gimle-cli-<version>.tar.gz` | `src/main/assembly/cli.xml` | Exactly `gimle-cli`'s own runtime dependency closure (`gimle-cli`, `gimle-core`, `gimle-module`, `gimle-pki`, slf4j, logback, snakeyaml, Bouncy Castle) — nothing else. Ships `bin/gimle`. |
| `gimle-hilmir-<version>.tar.gz` | `src/main/assembly/hilmir.xml` | Exactly `gimle-hilmir`'s own runtime dependency closure (`gimle-hilmir`, `gimle-core`, slf4j, logback, snakeyaml). Ships `bin/hilmir`. |

Each archive's `bin/` script (`src/main/dist/bin/gimle`, `src/main/dist/bin/hilmir`) builds its
classpath from every jar under its own sibling `lib/` directory at runtime, regardless of the
caller's working directory. Java selection precedence in both scripts: an explicit `JAVA_HOME`
always wins; otherwise a bundled `jre/<component>/` is preferred if present (see below); otherwise
plain `java` on `PATH`. `bin/hilmir` additionally exports `GIMLE_HOME` so Hilmir can locate its own
install root (in particular `modules/`) without guessing from `java.class.path`.

After assembly, `postprocess-archives` (via `maven-antrun-plugin`, using Ant's own `<checksum>`/
`<copy>` tasks rather than a shell script so it runs the same on every OS including Windows, where a
hardcoded `/bin/sh` has no equivalent) writes a `sha256sum -c`-compatible `.sha256` file next to each
archive and copies the one combined CycloneDX SBOM this module generates (`cyclonedx-maven-plugin`,
covering `gimle-dist`'s whole resolved dependency graph) to a per-archive `-cyclonedx.json` name.

## Optional: bundling a JRE (`dist-with-jre` profile)

`mvn clean install -pl gimle-dist -am -P dist-with-jre` additionally jlinks a minimal, trimmed JRE
for each of the eight process kinds that only ever run the platform's own known code
(`gimle-controlplane`, `gimle-mimir`, `gimle-fafnir`, `gimle-muninn`, `gimle-andvari`, `gimle-pki`,
`gimle-hilmir`, `gimle-cli`), using `--add-modules` lists duplicated from each of those modules' own
`gimle.runtimeImage.jdkModules` pom property (`java.home/bin/jlink`, `--strip-debug`,
`--no-header-files`, `--no-man-pages`), one output directory per component under
`target/jre-images/<component>/jre`. The `platform`/`cli`/`hilmir` assembly executions are then
overridden (by execution id) to use `-with-jre` variant descriptors that additionally copy each
relevant component's own jlinked JRE into the archive under `jre/<component>/`.

Deliberately excludes `gimle-agent` and `gimle-worker`: both dynamically load code this feature never
sees ahead of time (the agent spawns arbitrary Vessel jars, the worker hosts arbitrary Gimlé modules
inside its own JVM via `ModuleLayer`), so a trimmed JRE for either could silently break a workload
needing a JDK module outside that trimmed set, with no way to detect the mismatch ahead of time.

The default (no-profile) build is completely unaffected by this profile's existence — no `jre/`
directory is added to any archive unless `-P dist-with-jre` is explicitly requested, and re-running
it a second time without `clean` first fails (each jlink output directory must not already exist).

The CycloneDX SBOM covers only `gimle-dist`'s resolved Maven dependency graph; a jlink-produced JRE
is never a Maven dependency, so it never appears in that SBOM regardless of this profile.

## Building

```sh
mvn -pl gimle-dist -am install                  # three archives, no bundled JRE
mvn clean install -pl gimle-dist -am -P dist-with-jre   # same three archives, each with a bundled JRE
```
